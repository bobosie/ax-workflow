# AX Spec — 規格產出（Specify）

## 🔍 Step 0 — 先 Recall（AX 全技能通則，最高優先）
動手前、或過程中一遇到**不確定／錯誤／卡關／要做技術決策**：**第一步先 `ax:recall "<關鍵字>"`**——查團隊知識庫（過往經驗／解法）＋ reference／playbook／SOP。命中就沿用或以它為基礎調整。
> ⚠️ recall 命中率約 60%@5：**「查無」≠「沒做過」**（知識庫本身可能就漏），recall 是**輔助參考、不是判斷有無先例的依據**。**「查遍」的定義＝memsearch top-5 ＋（涉本專案時）掃一次 `doc/lessons-learned/` ＋ 最多換 1 次關鍵字**；到此仍無就自己想，別無限 retry、也別因查無就斷定「首次遇到」。

為「規格漸進成長、且常被外部客戶在 UAT 調整」的專案，產出**剛好高度**的前期規格。核心信念：規格的工作不是消滅變更，是**縮小每次變更的爆炸半徑**——把波動關進單一層，讓每次客戶調整只觸發最小的開發+測試迴圈。

> **先判斷該不該用**：本 skill 針對「中型以上、跨 session、值得長期維護」的功能。五行 bug fix / 一次性撈資料 → 直接寫、不啟動完整規格儀式（規格重量配任務重量）。

## 架構鐵律（先畫這條線）

**API 邊界畫在「領域模型」，不畫在「畫面」。** 對功能裡每個元素問一句：
> 「客戶說『我要它長得不一樣』時，這個東西會變嗎？」
- **不會變** → 核心（後端守，API 只吐這個，規格寫深）
- **會變** → 外殼（前端各自吸收，規格寫淺、預期會變）

## 執行步驟

1. **recall + 讀憲法**：先 `memsearch search "<功能關鍵字>"` 查過去解法；讀專案的 constitution（即專案的 CLAUDE.md 或架構設計文件）（技術棧、命名、log 脫敏、API 帶 trace_id 等全域約束），全程套用。

2. **核心/外殼分流**：用上面那句準則，把功能元素分兩堆。列出來給使用者確認邊界。

3. **產 Core Spec（一律強制，寫深）**——深在**正確性風險所在的軸**：
   - **計算風險型**（賠率/派彩/結算）→ 用 Given/When/Then 驗收條件 + **具體 Expected 數值** + **標來源**（試算/規則文件/參考競品，**禁止臆測**，查不到就進待確認清單）。每種情境各 ≥1 條，邊界 ≥3 條。
   - **資料/狀態風險型**（CRUD/狀態機/併發）→ 用**資料模型 DDL（欄位/型別/唯一鍵）+ 原子操作 SQL + guard/error code/idempotent 行為描述**（race condition 防護）。
   - 兩型都不寫 UI。

4. **產 Shell Spec（有畫面才寫，寫淺、可拋棄）**：
   - 複刻型（抄競品）：**參考物連結/截圖 + 差異清單**（參考物本身就是最精確的規格，也最好餵 AI）。
   - 列變體（如歐式/美式）。
   - 標「預期客戶 UAT 調整點」→ 這些點用 test ID + 元件複用，讓改動便宜。

5. **產 API Contract（有前端消費才寫）**：endpoint 從**核心領域模型**萃取（**嚴禁從畫面萃取**）；OpenAPI + mock server（如 Stoplight prism，需另裝）讓前端對 mock 並行；後端先寫、前端 review。

6. **多階段功能 → Phase × 完成標準矩陣**：切成可獨立驗收的 Phase，每 Phase 寫**可機器驗證的 Done**（測試綠/實際操作成功，不是「大概做好」）。

7. **待確認清單**：把「動手前必須拍板」的問題集中列出，點名「需要誰決定」——這些沒清掉不動工。

## 顆粒度標尺（剛好那欄＝要求）

| 產物 | 太粗 | ✅ 剛好 | 太細 |
|------|------|--------|------|
| 計算型 AC | 「要正確結算」 | 「Given 對莊下注100，When 莊贏賠率1:0.95，Then 餘額+95扣5%水錢」 | 把 UI 像素/動畫寫進 AC |
| 資料型核心 | 「存下注紀錄」 | 完整 DDL + `UNIQUE(...)` + 條件 UPDATE + affected-rows 語意 | 前期就定死 index 調優策略 |
| breadboard | 「做個輪盤」 | Places/Connections 文字拓樸 | 畫完整 wireframe 標顏色字級 |
| 外殼 | 「做得好看」 | 參考物 + 差異清單 + 變體 | 前期定死每個 hover/breakpoint（客戶還會改） |

## 完成定義（交付前自檢）

- [ ] 核心/外殼邊界已畫並經確認
- [ ] Core Spec：每情境有 AC、Expected 標來源不臆測、邊界 ≥3
- [ ] Shell Spec（若有畫面）：複刻型有參考物+差異、標出預期調整點、未觸及 API 契約
- [ ] API Contract 從領域模型萃取、mock 可跑
- [ ] 多階段有 Phase×Done 矩陣（可驗證）
- [ ] 待確認清單非空則已點名負責人
- [ ] 規格與 code 同進 PR（living artifact，不是開發前一次性文件）

## 反模式（別做）

- 把 API 綁在畫面上（客戶改皮膚就得改後端）——最常見的死法。
- Expected 由開發者自己猜、不標來源。
- 對外殼用 SpecKit/Tasks 這種重工具（會被客戶改到 spec drift 燒死）。
- 對五行小改動硬跑完整規格儀式。
