將目前對話中的**所有工作進度**暫存到 stash 目錄（`${AX_STASH_DIR:-$HOME/.ax/stash}`，未設 env 用預設，用前 mkdir -p），包含主 Agent 和所有隊友（子 Agent）的進度。

> **首次執行告知**：`mkdir -p` 前先判斷 stash 目錄是否已存在；**若不存在（首次使用）**，建立後在回報末尾附一行 `[AX] 首次執行：stash 目錄已建於 <實際路徑>（要改路徑：在 ~/.claude/settings.json 的 env 設 AX_STASH_DIR）`。之後的呼叫**靜默**、不再提示。判斷寫法：`[ -d "$STASH_DIR" ] || FIRST=1; mkdir -p "$STASH_DIR"`。

**若本次是 `/mission` 任務，還必須快照 mission 的結構**（經驗上下文、changeTypes、對抗審查計畫、pending CRITICAL、TDD 狀態），否則 resume 恢復後會遺失 mission 做法、無從重建。

> **stash = 先收割、再暫存**：stash 通常代表「這輪先放著、要開新 session 繼續」。因此**在暫存進度之前，必須先隱含執行 recap（`ax:recap`，若你的環境無此指令則跳過收割並提示）**，把本次 session 的經驗教訓收割完（確認收完，或確認無素材可收），避免開新對話後經驗流失。「先收，確定收完之後再 stash」——詳見下方步驟 1。

## 執行步驟

1. **先收割經驗（隱含 recap，最重要，先於一切）**：
   - 本次 session 累積的經驗（踩過的坑、成功流程、關鍵參數、使用者修正）若不先收割，開新對話後就流失了。所以 stash 前**先隱含執行 `ax:recap`（若你的環境無此指令則跳過收割並提示，直接進 stash）**。
   - 完整走 recap 流程（自主收割、不等確認）：回顧掃描 → 輸出經驗摘要（事後記錄，不停下等回覆）→ 分類產出（feedback / reference memory、lessons-learned、必要時 proto-skill）→ 索引更新。跨裝置/跨環境同步由你環境的 hook（若有）處理。
   - **recap 自主完成後（產出已寫入），直接進行下面的 stash 步驟——無需等使用者確認摘要。** 這是硬性順序：先收完再 stash，不可先 stash 再收。
   - **context 用量守門（重要）**：/stash 的常見動機正是「context 快滿、要開新 session」，但完整 recap 是重型操作（回顧整段對話 + 掃 stash + 寫多檔 + 可能產 playbook），在近滿 context 上貿然全跑會撞壓縮門檻（100+ 條對話時，過長的請求易觸發 cache-control 相關的 400 錯誤）或收出殘缺低品質記憶。因此：**若 context 已接近上限**（使用者說「快滿了」、本 session 對話/工具呼叫已非常長、或收割中途出現壓縮/400 徵兆）→ **降級為「輕量骨架收割」**：只在 stash 檔記下「踩坑清單 + 待沉澱項 + 預計產出類型」，**不**實際寫 memory/lessons/playbook，並在「恢復指引」註明「本次輕量收割，新 session 開啟後請手動 `ax:recap` 完整沉澱」。（對齊 auto-harvest Stop hook 的 >84% 保護閥精神。）
   - **例外（可跳過收割，但要在回報中註明）**：
     - 本次 session 純快速操作 / 純唯讀查詢，無踩坑、無新模式、無新參數 → recap 判定「無素材可收」，明確回報後直接繼續 stash。
     - 本次 session 稍早已執行過 recap、之後無新的可收割經驗 → 註明「本 session 已收割」後跳過，直接 stash。
   - **收割 ≠ stash，兩者都要**：recap 存的是「可複用的知識資產」（memory / lessons / prompt）；stash 存的是「這個未完成任務的工作進度上下文」。互補、不可互相取代。

2. **盤點所有參與者的進度**：
   - 回顧主 Agent（自己）做了什麼、做到哪裡
   - **盤點所有已啟動的隊友（子 Agent）**：檢查每個隊友的完成狀態和實際產出
   - 對於已完成的隊友：記錄其產出的檔案和結果摘要
   - 對於執行中/失敗/被中斷的隊友：**主動檢查其實際產出**（檢查檔案是否已寫入、行數、完整性），不要只看回報狀態
   - 對於撞到額度限制或被 kill 的隊友：用 `find`/`wc -l` 等指令確認它們在中斷前實際完成了多少工作

3. **若本次為 `/mission` 任務，盤點 mission 上下文**（供 resume 重建 mission 模式）：
   - Step 0 載入的經驗上下文摘要（必守的 feedback 規則、相關過去經驗）
   - `changeTypes`（ui / backend / plan / data）
   - 執行方式（對話層 / Workflow 預設 / Workflow 加碼 / 長跑 PROGRESS.md）
   - 對抗審查計畫與進度（用了哪些 lens、意圖守門人 met/partial/missed）
   - 實證閘門 pending CRITICAL（哪些 CRITICAL 還沒實證、還沒修）
   - TDD 狀態（紅燈測試寫了沒、綠燈了沒、哪些 spec）

4. **建立或更新 stash 檔案**：
   - 路徑：stash 目錄下 `{日期}-{簡短描述}.md`
   - 如果已有相同主題的 stash，更新它而非建立新的

5. **檔案格式**：

6. **回報使用者**：告知已 stash，摘要列出：
   - **收割結果**：recap 產出了什麼（或「無素材可收」/「本 session 已收割」/「環境無 recap 指令，已跳過」）
   - 主 Agent 已完成 / 待完成項目數量
   - 隊友數量及各自狀態（完成/中斷/失敗）
   - 隊友的實際產出統計（檔案數、行數）
   - 若為 mission：是否已保存 Mission 上下文段

## 注意事項

- **stash 前一定先收割（隱含 `ax:recap`，環境無此指令則跳過並提示）**：先收完、確認收完（或確認無素材 / 本 session 已收割 / 無 recap 指令）再 stash，順序不可顛倒。recap 存「可複用知識」（memory / lessons / prompt），stash 存「未完成任務的工作進度」——兩者互補、不可互相取代
- stash 的目的是讓**未來的新對話**能快速恢復上下文，所以要寫得夠詳細
- **隊友的進度是 stash 的一等公民**：不能只記錄「有派出隊友」，必須記錄每個隊友實際做了什麼、產出了什麼檔案
- 隊友被中斷（額度限制、timeout、kill）≠ 沒有產出。**必須檢查檔案系統確認實際完成度**
- **mission 任務必須填「Mission 上下文」段**：resume 靠它重建 mission 模式（記憶載入、對抗審查、實證閘門、TDD、收尾經驗）。漏填 = 恢復後只會照 todo 硬做、遺失 mission 的所有做法
- **待完成項標註形狀**（快速操作 / 偵探排查 / 開發實作）：讓 resume 能正確決定哪些 todo 要套 mission、哪些直接做
- 記錄具體的檔案路徑、指令、錯誤訊息，不要只寫抽象描述
- 恢復指引要具體到可以直接複製貼上執行的指令
- status 說明：`in-progress`（進行中）、`blocked`（等待外部回應）、`done`（已完成）
